# Job Scan Console — project instructions

A self-serve job-search system: the `/scan-jobs` skill (in `.claude/skills/`) scans Indeed against `profile.md` and writes timestamped reports to `reports/`; the static console in `console/` displays both. Nothing in this repo executes scans — Claude runs them, in sessions like this one.

## If `profile.md` does not exist yet → onboard the user

Run setup conversationally, one step at a time. Never invent answers, and never keep template/example values the user didn't choose.

1. **Find the resume.** Look for a resume PDF or .docx in this folder and in its parent (the user's Claude-Workshop folder). If none is found, ask where it is. If it's a Google Doc: the easiest route is **File → Download → PDF** into the Claude-Workshop folder; if the user has the Google Drive connector connected, offer to fetch the Doc directly instead.
2. **Create `resume.md`.** Write a faithful markdown transcription of the resume **next to the original in the parent Claude-Workshop folder — NOT inside this repo** (it must never be committed or served). From now on `resume.md` is the canonical machine-readable resume: read it instead of re-parsing the PDF, and make future resume edits there at the user's request. The original PDF/Doc remains the formatting source of truth.
3. **Build `facts.md`** at this repo's root (beside `profile.md`) — the fact registry that `/apply` tailors résumés against and its honesty lint checks claims against. One markdown row per fact, this exact schema (a parse contract — reproduce it verbatim):

   `| id | kind | value | source_text | provenance |`

   `kind` ∈ `metric` / `title` / `date` / `credential` / `deliverable`. `provenance` ∈ `résumé` / `self-reported` / `attested`.

   Extract every number, title, date range, and credential from `resume.md` — **including tenure**: any stated span of experience, overall or per-role (e.g. "6 years running youth education programs"), becomes its own `metric` row in addition to the `date` rows for the ranges themselves, with the verbatim résumé line as its `source_text`. A duration like that is *implied* by the date ranges rather than written down as a number of its own — but the lint script compares literal numbers against literal registry rows and deliberately does no date arithmetic, so without this row a true, unremarkable summary line reads as an unbacked claim. The same failure class shows up whenever one résumé sentence carries facts about more than one object: **scope every row's `value` to the specific thing it describes**, and give each object its own row rather than letting two facts share one or letting a row's scope be inferred from a neighbouring claim. Worked example — "Ran youth education programs across 4 sites, rolling out a shared scheduling tool to all 4" is two facts, not one: a row `value: 4 sites (education programs)` and a separate row `value: 4 sites (scheduling tool rollout)`, both citing the same `source_text` sentence. A row whose `value` reads just `4 sites`, or one scoped only to the programs, won't back a later claim about the tool's rollout, and — worse — could wrongly appear to back it: the lint script compares literal numbers against literal registry rows, not against the sentence a row came from, so an under-scoped row can either falsely fail a true claim about the other object or falsely certify it. For each row, `source_text` **must be the verbatim line from `resume.md`** — never paraphrase; a paraphrase that survives a skim becomes canonical and silently poisons every check downstream. `provenance` is `résumé` for every extracted row. Show the table to the user and have them confirm it by checking `source_text` against their own résumé — it's a diff against a document they already know, not a comprehension test. Fix anything wrong before moving on.

   Then ask 3–4 reservoir questions for accomplishments that never made it onto the résumé ("what have you shipped that isn't on here?"). Add each as a new row with `source_text` empty and `provenance: self-reported`. This is what makes tailoring possible for career-changers, whose résumés are written for the field they're leaving and omit transferable evidence — don't skip it. Tell the user a `self-reported` row can be **attested** once (an explicit "I stand behind this and can defend it in an interview"), which sets its provenance to `attested` and stops it triggering lint warnings later; they can do this now or anytime by re-running this step.
4. **Interview for preferences.** A resume says what they've done, not what they want — ask, with brief examples: target titles (2–3, plus any explicit exclusions), location (remote / a city / both), salary floor, job type (full-time / contract / both), dealbreakers (e.g. unpaid roles, mandatory relocation), freshness window (default 48 hours).
5. **Write `profile.md`** at this repo's root, from `profile.template.md`: Background drafted from resume.md; criteria from the interview; the Scoring rubric **personalized** — name the substance dimension after their focus and write its 0–4 anchors against their actual skills/domains from resume.md. Keep every `##` heading name exactly as the template has it (the console parses them). In `## Job type`, name **only the types they want** — never mention an excluded type, even to rule it out: the console matches type names literally, so "Full-time roles are out" renders Full-time as an *active* filter. Exclusions belong in `## Dealbreakers`. Leave Calibration anchors empty until after their first scan. Delete the template's HTML comment block.
6. **Start the console.** From this folder, run `python3 -m http.server 8642 --bind 127.0.0.1` as a background task — bind to localhost only, since the served folder now holds `applications/` (tailored résumés) and `facts.md`, and the default binds every interface, making them readable across the user's LAN. Then have the user open http://localhost:8642/console/ and confirm their profile fields appear.
7. **Offer next steps:** run `/scan-jobs` now for a first report, and optionally create a scheduled task for automatic daily morning scans.

## Ongoing rules (once `profile.md` exists)

- **Profile edits happen here in sessions** ("raise my salary floor to $110K") by editing `profile.md` — the console is read-only and reflects the file on next refresh.
- **Reports:** `/scan-jobs` writes `reports/{YYYY-MM-DD-HHmm}.md`. Keep the `**Fit:** N/10` line format — the console parses it.
- **Never fabricate scan results.** If the Indeed connector's tools (`search_jobs` / `get_job_details`) are unavailable, say so and point the user to add the Indeed connector to their Claude account.
- **After the first scan**, offer to record Calibration anchors in profile.md's rubric from the real scored results.
- **If `resume.md` changes, re-run the registry step (onboarding step 3) for the affected rows.** Each `facts.md` row quotes `resume.md` verbatim in `source_text`; when a quoted line is edited, the row silently stops matching its own source and the "confirmed against the résumé" guarantee expires with nothing announcing it. Re-extract and re-confirm rather than leaving a stale quote.
- `profile.md`, `facts.md`, `reports/*`, `applications/`, and `resume*` are gitignored — personal data never gets committed. Keep it that way.
